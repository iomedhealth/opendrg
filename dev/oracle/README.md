# MS-DRG v44.0 test oracle (CMS Java grouper over CMS TESTDB)

CSV fixtures produced by running **CMS's own Java MS-DRG grouper (v44.0, msdrg-core 44.0.0.3)** on
macOS over **CMS's mainframe test claim database (TESTDB, 9,864 records)**, for an R implementation
to test against.

**Runtime options used for the fixtures** (`gov.agency.msdrg.model.v2.RuntimeOptions`, pinned in
`java/src/oracle/GrouperEngine.java`, echoed per claim in the `opt_*` columns of
`testdb_v440_expected.csv`):

| option | value | why |
|---|---|---|
| `poaReportingExempt` | **per record** from TESTDB column 7 (POALOG): `X` → `EXEMPT` (4 records), anything else (`Z` ×9,859, `Y` ×1) → `NON_EXEMPT` | the record layout carries this hospital POA-reporting indicator and CMS's wrapper maps it exactly so; the value is in `testdb_v440_input.csv` (`poa_logic`, `hospital_poa_status`) |
| `markingLogicTieBreaker` | `CLINICAL_SIGNIFICANCE` | no per-record flag exists; the grouper's documented default and what CMS's wrapper hard-codes |
| `computeAffectDrg` | `COMPUTE` | idem |
| `MsdrgOption.TRACE` | consumer attached (text trace captured per claim, see `*_trace*.csv`) | only way to see clusters / matched formulas; verified not to change any output |

A second expected-results set, `testdb_v440_expected_poa_unknown.csv` (+ `_dx`/`_pr`), was produced
with `poaReportingExempt = UNKNOWN` for every claim; `testdb_v440_poa_sensitivity.csv` lists the
claims whose results differ (**73 claims** — exactly the HAC claims: they become RTC 10
`HAC_STATUS_INVALID_POA_N_OR_U`, DRG 999, MDC 0, HAC status `FINAL_DRG_UNGROUPABLE`).

Headline results (full run, `java/run.sh`):

| check | result |
|---|---|
| TESTDB records read / grouped with v44.0 through the official Java API | **9,864 / 9,864** (0 grouper errors, 0 parse failures) |
| CMS mainframe wrapper (`MSDRGMF440.jar`, version picked by discharge date) vs expectation embedded in each TESTDB record, whole 1162-byte output | **9,864 / 9,864 identical** (same result as the z/OS install test, incl. the RTC 98/99 date edge cases) |
| this harness's API output (auto version 40.0–44.0, rendered in mainframe format) vs the wrapper's output | **1,922 / 1,922 identical** (all records whose discharge date selects a v2-model version) |
| v44.0 API output vs embedded expectation, records CMS graded with v44.0 | **77 / 77 identical** (whole output) |
| v44.0 API output vs embedded expectation, all records (most were graded by CMS with v39.1–v43.1) | 8,290 / 9,864 return-code+DRG agreement (84.0%) — differences are version logic/code-set changes, see below |

## How to re-run

```bash
/Users/gabriel.maeztu/repos/open-grd/dev/oracle/java/run.sh            # everything (~15 s): fixtures, POA-UNKNOWN run, table dump, validation
/Users/gabriel.maeztu/repos/open-grd/dev/oracle/java/run.sh --version 430 --mode api   # another bundled version -> output/testdb_v430_*
/Users/gabriel.maeztu/repos/open-grd/dev/oracle/java/run.sh --help
```

`run.sh` compiles `java/src/oracle/*.java` with `/usr/bin/javac --release 17` and runs
`oracle.OracleHarness`. CLI options of the harness:

| option | meaning |
|---|---|
| `--version 440` | grouper version: one of `400 401 410 411 420 421 430 431 440` (all bundled in msdrg-core-44.0.0.3.jar) or `auto` (select by discharge date exactly like CMS's wrapper; 39.0/39.1 records are then skipped because those versions only exist in the v1 model inside the mainframe jar) |
| `--mode api\|wrapper\|both` | `api` = official Java API (the fixtures); `wrapper` = call CMS's `gov.cms.grouper.mainframe.Msdrg.processMsdrg()` on the 638-byte input and diff against the embedded expectation; `both` = both plus API-vs-wrapper diff |
| `--prefix NAME` | output file prefix (default `testdb_v<version>`) |
| `--poa-status per-record\|NON_EXEMPT\|EXEMPT\|UNKNOWN` | `poaReportingExempt`: per record from column 7 (default) or forced for every claim |
| `--suffix S` | appended to the expected/trace/comparison file names (e.g. `_poa_unknown`) |
| `--skip-inputs` | do not rewrite the `_input*` and `_cms_embedded*` files |
| `--no-trace` | do not attach the trace consumer / write the `_trace*` files |
| `--lenient-numeric` | trim age/sex/discharge-status before parsing (see caveat on left-justified ages) |
| `--limit N` | only the first N records |

`run.sh dump [--version 440]` runs only `oracle.DataDump` (the `v440_*.csv` tables).
Environment overrides: `MSDRG_EXTRACT` (base of the extracted CMS package), `TESTDB`, `OUT`, `JAVA`, `JAVAC`.

| 599-637 | CLAIM-OPT-DATA | free-text description of the test case (e.g. `PDX:dxc0116`, `change15_add_cluster_...`) |
| 638 | DEBUG-IND | blank |

| 839-840 | RTC | **expected** return code (00/01/07/98/99 occur) |

The version ids embedded by CMS: 00139000 ×14, 00139100 ×7926, 00140000 ×186, 00140100 ×292,
00141000 ×315, 00141100 ×62, 00142000 ×115, 00142100 ×107, 00143000 ×748, 00143100 ×20,

Columns 839-2000 are exactly the 1162-byte output record of PBL-060 table 28 (`OUT-CMSDRG-RTC` …

## API calls used (`java/src/oracle/*.java`)

Runtime configuration (identical to CMS's wrapper and the PBL-161 sample):

```java
MsdrgRuntimeOption runtimeOption = new MsdrgRuntimeOption();
RuntimeOptions options = new RuntimeOptions();
options.setComputeAffectDrg(MsdrgAffectDrgOptionFlag.COMPUTE);
options.setMarkingLogicTieBreaker(MarkingLogicTieBreaker.CLINICAL_SIGNIFICANCE);
options.setPoaReportingExempt(poaLogic == 'X' ? EXEMPT : NON_EXEMPT);   // per claim
runtimeOption.put(MsdrgOption.RUNTIME_OPTION_FLAGS, options);
Processable<MsdrgClaim, MsdrgOption, MsdrgRuntimeOption> component =
    new gov.agency.msdrg.v440.MsdrgComponent(runtimeOption);           // via reflection on the version
component.reconfigure(runtimeOption);
MsdrgClaim claim = new MsdrgClaim(input);
component.process(claim);
MsdrgOutputData out = claim.getOutput().orElseThrow();
```

Input mapping (`ClaimMapper`), replicating `MsdrgMainframeWrapper.populateClaimWithModelV2`
(decompiled in `docs/MsdrgMainframeWrapper.javap.txt`):

| record field | API call | semantics |
|---|---|---|
| AGE | `withAgeInYears(Integer.parseInt(raw3))` | parse failure (blank / left-justified) ⇒ builder default **0** |
| SEX | `withSex(1→MALE, 2→FEMALE, else UNKNOWN)` | blank/`0` ⇒ `UNKNOWN` |
| DISCHARGE STATUS | `withDischargeStatus(MsdrgDischargeStatus.getEnumFromInt(parseInt(raw2)))` | parse failure ⇒ not set |
| DX1 | `withPrincipalDiagnosisCode(new MsdrgInputDxCode(code.trim(), poa))` | blank slot ⇒ no principal (grouper then reports a `null` pdx, RTC 7) |
| DX2..25 | `withSecondaryDiagnosisCodes(list)` | blank slots skipped (list compacted, order kept) |
| POA char | `GfcPoa.fromChar(c, GfcPoa.BLANK)` | blank or unknown char ⇒ `BLANK`; Y/N/U/W/1/E recognised |
| PROC1..25 | `withProcedureCodes(list of new MsdrgInputPrCode(code.trim()))` | blank slots skipped |
| — | `withAgeDaysAdmit(-1)`, `withAgeDaysDischarge(-1)` | as the wrapper; admission dx never set |
| POALOG | `RuntimeOptions.setPoaReportingExempt` | `X` ⇒ `EXEMPT`, anything else ⇒ `NON_EXEMPT` |
| ADATE, PRDATES | — | ignored by CMS's wrapper |

Output extraction (`OracleHarness.runApi`): `getFinalGrc/Mdc/Drg/BaseDrg/Severity/MedSugType`
(sic — the real method name is `getFinalMedSugType`, the PDF misspells it `getFinalMedSurgType`),
`getInitial*`, `getFinalDrgSdxSeverity`, `getInitialDrgSdxSeverity`, `getHacStatus`,
`getNumHacCategoriesSatisfied`, `getGrouperFlags()` (incl. `getAdmitDxGrouperFlag`), `getPdxOutput`,
`getSdxOutput`, `getProcOutput`, and per code `isDiagnosisRecognizedByGrouper`,
`getDiagnosisAffectsDrg`, `getFinal/InitialSeverityUsage`, `getPoaErrorCode`, `getHacs`
(`MsdrgHac.getHacNumber/getHacStatus`), `getLegacyFlagString`, `isProcedureRecognizedByGrouper`,
`getProcedureAffectsDrg`, `isProcedureIsOperatingRoomProcedure`, `getHacUsage`.

`LegacyFormat` re-creates the mainframe 1162-byte output from the API output exactly as
`MsdrgMainframeWrapper.extractFromClaimWithModelV2 / mapGrouperFlagOutputWithModelV2 /
mapDxFlagOutputWithModelV2` do (verified: 1,922/1,922 byte-identical to the wrapper). The mainframe
encodings it implements, also written to the CSVs as `*_mf` columns:

* GRFLGS: `%02d` nHAC · final CC/MCC impact (`MsdrgSeverity` level MCC→1, CC→2, NON_CC/NONE→0) ·
  initial impact · HAC status (NOT_APPLICABLE 0, FINAL_DRG_NO_CHANGE 1, FINAL_DRG_CHANGES 2, FINAL_DRG_UNGROUPABLE 3).
* DX block (25): `1` · affects-DRG (NONE 0, INITIAL 1, FINAL 2, BOTH 3) · CC/MCC category
  (final/initial usage → 1 MCC/MCC, 2 CC/CC, 3 NEITHER/MCC, 4 NEITHER/CC, 5 MCC_EXCLUDED, 6 CC_EXCLUDED,
  7 MCC_EXCLUDED_BY_DRG_LOGIC, 8 CC_EXCLUDED_BY_DRG_LOGIC, else 0) · up to 5 × (`%02d` HAC number +
  usage digit NOT_ON_HAC_LIST 0 / MET 1 / NOT_MET 2 / EXCLUSION 3 / EXEMPT 4, `000` when absent) · `0000000`;
  unrecognised code ⇒ `0` + 24 spaces.
* PR block (20): `1` · affects-DRG · OR flag · `%02d` per HAC usage (HAC_08 01, HAC_10 02, HAC_11 03,
  HAC_12 04, HAC_13 05, HAC_14 06) · zero fill; unrecognised ⇒ `0` + 19 spaces.
* BUFF: `%04d` base DRG, severity level (MCC 1, CC 2, NON_CC 3, NONE 0), med/surg (MEDICAL 1,
  SURGICAL 2, NONE 0), `%04d` initial DRG, `%04d` initial base DRG, initial severity, initial
  med/surg, `"001" + version + "00"`.

What the output model does **not** expose per procedure: cluster membership, the bilateral /
fusion-count / multiple-trauma function results (`BilateralNode` marks `CodeFlag.BILATERAL` on
internal `MsdrgProcedureCode` objects that never reach `MsdrgOutputPrCode`). Cluster ids are
therefore taken from the trace; the bilateral/fusion outcome is visible only indirectly through the
matched formula in `testdb_v440_trace.csv` (e.g. claim 9375: `MDC8:DRG461:[MCC & BILATERAL]` with
matched attributes `righthip,lefthip,MCC`).

`testdb_v440_trace.csv` — per claim, parsed from the grouper's own `TraceUtility` text:

| column | meaning |
|---|---|
| `clusters` | procedure clusters recognised on the claim, `code{mdc restriction set}`, `;`-separated, e.g. `Z@7093{10\|29}` |
| `initial_mdc_path` / `final_mdc_path` | MDCs evaluated in order (`0>5>29`: pre-MDC, the PDX MDC, then the reroute to MDC 29 "unrelated OR procedure") |
| `initial_matches` / `final_matches` | formula rows that matched, `MDCn:DRGd:[formula]`, `;`-separated; `DRG0` rows are reroute rows (the reroute target's own match is not traced by the grouper) |
| `initial_matched_attributes` / `final_matched_attributes` | the attributes the matched formula consumed (`,`-separated, per match `;`-separated) |
| `hac_formulas_matched` | e.g. `HAC 5 (SDX:HAC05)` |

`testdb_v440_trace_codes.csv` — per code, parsed from the trace, `kind` = `PDX`/`SDX`/`PROC`/`CLUSTER`,
`seq` aligned with the input files: `poa, mdc (PDX only), dxcat (PDX), clin_sig, severity (the code's
own CC/MCC level before exclusions), hac (HAC lists the dx is on), attributes` (`|`-separated
attribute list names as used in the formulas), `cluster_ids` (PROC), `mdc_suppression` (CLUSTER).
The PDX attribute list in the trace is already filtered by MDC suppression; do not read the trace's
"mask" for anything but the MDC path (the grouper de-duplicates attributes when printing it, which
can hide an unsuppressed duplicate carried by a cluster).

### Sensitivity to `poaReportingExempt` (`testdb_v440_expected_poa_unknown.csv`, `testdb_v440_poa_sensitivity.csv`)

Re-running every claim with `poaReportingExempt = UNKNOWN` (instead of the per-record X/Z value)
changes **73 of 9,864 claims** — precisely the 73 claims on which a HAC formula was satisfied with a
POA of `N` (`hac_status = FINAL_DRG_CHANGES` in the main run). With `UNKNOWN` the grouper cannot
decide whether the hospital reports POA and makes them ungroupable: `final_grc` 0 → 10
(`HAC_STATUS_INVALID_POA_N_OR_U`), `final_drg` → 999, `final_mdc` → 0, `final_severity` → `NONE`,

claim is affected (the 4 POALOG `X` claims carry no HAC). `EXEMPT` would instead mark every HAC
`HAC_NOT_APPLICABLE_EXEMPT` and keep the initial DRG.

## Caveats

* **Left-justified ages.** 1,923 TESTDB records have ages like `"55 "`, `"25 "`, `"0  "`.
  CMS's wrapper feeds them to `Integer.parseInt` untrimmed, which fails, so the grouper is run with
  the builder default **age 0**; the fixtures replicate this (`age = 0`, `age_parsed = false`,
  `age_raw` keeps the bytes). It makes no difference to any output in this file: a `--lenient-numeric`
  run (age 55 etc.) yields identical final DRGs for all 9,864 claims. Pick whichever your R tests
  prefer; the expected files are the same.
* **Sex.** 43 records have a blank sex and one has `0`; both map to `MsdrgSex.UNKNOWN`
  (no RTC 4 occurs in this file because none of those claims reaches a sex-dependent DRG).
* **Dates are not inputs to the grouper.** Admission date and procedure dates are ignored; the
  discharge date only selects the version in `auto`/wrapper mode. With `--version 440` the two
  records that CMS graded RTC 98/99 (claims 8117 and 8119: discharge dates `20210930` → before
  10/01/2021, and `xxxxxxxx`) are simply grouped by v44.0 (RTC 0, DRG 914). Those are the only two
  `rtc_match = false` records with `embedded_version` empty.
* **Only 77 TESTDB records were graded by CMS with v44.0.** The remaining embedded expectations are
  for v39.0–v43.1 and must not be used as v44.0 truth; use `testdb_v440_expected*.csv` (this run)
  for v44.0 and `testdb_v440_cms_embedded*.csv` only together with `version_id`.
* **POA.** TESTDB diagnoses carry POA `Y`/`N` (and some blanks); hospital status is `NON_EXEMPT`
  except 4 claims with POALOG `X`. `poa_error_code` is `POA_NOT_CHECKED` unless the code is on a HAC
  list.
* `grouper_flags_api` / `flags_api` are the API's own legacy strings (`toString()` of
  `MsdrgGrouperFlags`/`MsdrgDiagnosisFlag`/`MsdrgProcedureFlag`) and use a *different* encoding from
  the mainframe `*_mf` columns (e.g. CC usage digit 5 vs category 2). Prefer the enum columns.
* 39.0/39.1 cannot be run through the v2 API; if needed, the wrapper path (`--mode wrapper`) gives
  their mainframe-format output (`testdb_vauto_wrapper_vs_embedded.csv` stores rtc/mdc/drg; the full
  output equals the embedded one anyway).
* **Trace-derived columns** (`cluster_ids` in `testdb_v440_expected_pr.csv`, everything in
  `testdb_v440_trace*.csv`) come from the grouper's human-readable `MsdrgOption.TRACE` text, not from
  the output model; the parser is `TraceParser.java`. Attaching the trace consumer was verified not
  to change a single output value (expected files identical with `--no-trace`). Bilateral / fusion /
  multiple-trauma function results are not exposed anywhere; only the matched formula shows them.
* The two "only in binary" DRG formula rows (MDC 5 `(ANY:ami) & (ami)`, MDC 15 `5`) and the `MDCnn`
  gate rows are dumped as-is; whether an implementation needs them is for the DRGLOGIC diff to
  decide (they never fire on TESTDB: no `initial_matches` in `testdb_v440_trace.csv` contains them).
